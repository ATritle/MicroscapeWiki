# Microscape Wiki

MzDunk’s community wiki for the Twitch-powered browser idle RPG Microscape. The site uses static HTML, CSS and JavaScript. GitHub Actions renders the `docs` sources into searchable HTML and deploys the generated `.seo-site` directory to GitHub Pages.

## Preview locally

From the repository root, install the pinned build dependencies and render the site:

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm check:seo
node scripts/preview-player-lookup.mjs 8065 ../.seo-site
```

To preview Player Lookup locally with real public profiles, run
`node scripts/preview-player-lookup.mjs 8065` and open
`http://127.0.0.1:8065/#/player-lookup`. This localhost-only server uses the public
community ranking index to resolve exact usernames, then reads current profiles
from Microscape. Unindexed characters may be missing from this preview.
The production `/player.json` Worker endpoint resolves names directly
through Twitch using the existing server-side app credentials. Neither command
publishes changes. Run `node scripts/check-player-lookup.mjs` to check profile
validation, cache isolation, skill math, sprite layers and existing feed behavior.
The original sprite and activity metadata in `docs/player-reference.json` is built
by `scripts/build-player-reference.mjs` from a captured public game build.

Name suggestions use the public player index at `microwiki.mhmm.pl` through
`/player-search.json`, with partial matches and a bounded close-spelling fallback.
The index may omit new characters; exact username lookup still goes directly
through Twitch and Microscape. The game's `currentWorldId` is an internal ID,
not its displayed world number. The client resolves it through
`meta.availableWorlds` on the authenticated game socket. No public directory was
found, so world information is omitted from the page until joinable world
numbers can be verified.

The public character endpoint also returns identical location, activity and HP
values for different players. Those fields are not verified live state and are
discarded by the Worker. The page labels them unavailable, including when an old
cached response still contains them. See `audits/2026-11-19-player-lookup-status.md`
for the comparison and evidence.

## Edit the wiki

- Edit `docs/guides.js` for guides, patch coverage and playable walkthroughs. Each guide has a permanent ID, sections, related article IDs and sources.
- Add combat tutorials in `docs/tutorials.js`. List the relevant foe, equipment and ability IDs so their reference pages link back to the tutorial.
- Edit `docs/reference.json` for catalog entries. An entry can include a summary, facts and tables. Keep existing IDs stable so saved links keep working. Add the patch date and link to the evidence when revising a beta-era value.
- Location entries use `mapImage` for the official map preview, with the image URL and its original width and height. Keep entrance requirements and dungeon chamber routes with the travel directions.
- Release pet profiles, map prices, eligible tasks, odds and sprites are stored directly in `docs/reference.json`. `docs/pets.js` retains the fallback generator for older beta catalogs.
- Pet directory tiles read `Vendor map option`, `Cost`, `Pet Map` and membership facts from those profiles. They showcase the Mork/Otis trade name and Audience Favor price, then identify the Pet Map received. The vendor map name is a trade option, not a second inventory item. No-map catches and archived beta pets retain distinct acquisition information.
- The Pets directory sorts by companion skill/type alphabetically, then pet name within each type, with archived beta companions last. This order is retained by its existing filters and pagination; general wiki search keeps its relevance ordering.
- Edit `docs/styles.css` for the visual theme. The original pixel-art village banner lives in `docs/assets`.

The November 19 launch comparison and verification are in `audits/2026-11-19-release`.
The release guide is generated by `scripts/enrich-release.mjs`; its public page is
`#/entry/release-changes`. Current factual definitions are preserved in
`docs/assets/game-data/release-2026-11-19.json`, alongside the unchanged beta evidence.
Removed beta records keep their routes and locally archived original artwork.

The release migration can be rehearsed with `node scripts/sync-release.mjs SNAPSHOT`,
followed by `node scripts/enrich-release.mjs SNAPSHOT` and
`node scripts/build-player-reference.mjs SNAPSHOT`. It expects the captured game files,
manifest, normalized beta and Acorn installation in the existing MicroscapeBuilds layout.
The migration starts from the frozen pre-release wiki commit; do not use it to overwrite
later manual changes without reviewing that baseline.

The November 18 audit and follow-up reports are also saved in `audits`. To repeat the
completeness check against a captured public build, run
`node scripts/audit-wiki.mjs --game-data path/to/snapshot/game-data.json --out audits/DATE --check-links`.
Run `node scripts/check-audit-updates.mjs SNAPSHOT` to verify every current item bonus

It validates every generated page before publishing. To check a change, open the site and try an affected deep link, a search, and the relevant filters.

## Search indexing and rollback

Activity Comparison shows **Estimated damage taken/hour** for combat choices.
It estimates basic melee HP loss before healing from enemy hit chance, average
damage roll and attack speed (two-second ticks), weighted by the modeled fraction
of each fight/preparation cycle spent fighting. Between-fight delays are assumed
damage-free. Equipment abilities are now auto-detected and share Gear Comparison's
editable ability, potion and learned-ability controls. Levels initially assume 1
because public profiles omit them; potions start off in Activity Comparison.
The results show both gear-only and selected-effect incoming damage. Stoneskin
reduces a hit by 1 on a proc without changing dodge; Shield Wall needs entered
maximum HP when damage is possible. The effect model also handles supported XP,
damage and attack-timing effects. Exact first-hit timing, spells/dragon breath/
poison from enemies, healing and survival downtime are excluded. Unsupported
encounters show Not modeled. Run `node scripts/check-activity-comparison.mjs`
for mitigation, effect power, custom timing, safe spots and zero-damage cases.

The Gear and Loadout Comparison at `/gear-comparison/` reuses Player Lookup's
username suggestions and read-only profile endpoint. A loaded profile also links
to it through **Compare loadouts**. The baseline remains immutable; only a local
copy is edited. Recent profiles are reused in memory for up to one minute, and
planning pages require manual refresh so background updates cannot discard edits.
Nothing is saved to browser storage or sent back to the game.

`docs/loadout-comparison.js` filters gear by slot, checks base-level requirements,
handles two-handed weapons/shields, renders both appearances with existing game
layers, and uses the shared combat model. Gear and spells above trained levels
receive labeled hypothetical estimates using the actual current levels, with
unmet requirements listed above the result. Requirements do not raise base stats.
Invalid slot/style combinations, missing arrows/spells and boss/special encounters
remain unmodeled. Each side has independent ability levels,
learned abilities, potion assumptions and spell upgrades. `docs/loadout-effects.js`
models supported stat, damage, XP and quick-attack effects, including finite enemy
HP and overkill. Defensive effects change incoming melee damage without inventing
survival downtime. The public profile does not expose ability levels or active
buffs: equipped abilities default to level 1, prayers off, temporary buff uptime
to 0%, and learned abilities to their permanent unlock. Potions assume maintained
boosts; super-potion rounding and same-skill stacking are labeled assumptions with
manual overrides. Focus requires an entered cast interval for hourly estimates.
Unsupported stateful effects are listed beside the result. Supplies, eating,
deaths, banking and group combat are excluded; four combat XP baselines remain
unverified. Evidence and assumptions are in
`docs/assets/game-data/loadout-effects-2026-11-21.json`.
Run `node scripts/check-loadout-comparison.mjs` and
`node scripts/check-loadout-effects.mjs` (baseline equivalence and effect cases).
Rebuild `docs/loadout-reference.json` using
`node scripts/build-loadout-reference.mjs GAME_DATA_JSON` after a game-data update.

Specific pages serve original static Open Graph cards at `/assets/social/`, with
their own title, summary, facts and artwork. `scripts/social-cards.mjs` generates
1200×630 PNGs during the SEO build using Sharp. `docs/share-artwork.json` contains
deduplicated thumbnails prepared from the captured public game artwork; regenerate
it with `node scripts/prepare-share-artwork.mjs CAPTURED_ASSET_DIRECTORY [...]`.
The build needs no network access for artwork. Player lookup and comparison cards
stay generic and never embed a player's profile or username. The home page keeps
its village banner. Legacy hash fragments cannot be read by Discord; open the page
and share its normal path URL. Discord may retain an older preview in its cache.

The SEO build uses the same `docs/app.js` renderer as the browser. It preserves the existing markup, CSS, tools and visible content while generating one HTML document per entry, directory and tool. `docs/seo.js` maps old hash links to stable paths such as `/items/rubber-boots/`, updates page metadata on navigation and retains old bookmarks. A root `<base>` keeps existing asset and citation URLs working on nested pages. Home, article and directory content is available in the initial HTML without executing JavaScript.

The original XP Calculator is at `/guides/experience/`, linked from Resources and Guides. Its optional username lookup uses the existing public profile endpoint through `docs/xp-player.js`; choosing one of the 16 skills fills its exact XP and its level using the same curve as Player Lookup. Partial-name and spelling suggestions use Player Lookup’s existing public `player-search.json` endpoint. Selecting a matching name loads the profile; arrow keys and Enter select results, and Escape dismisses them. Target level, XP per action and manual entry remain available. Pending requests and suggestion timers are canceled when the name changes or the reader leaves the page. No usernames or player snapshots are saved into the static pages, page URLs or browser storage. Run `node scripts/check-xp-player.mjs` to verify profile and suggestion validation, XP thresholds, zero-XP skills, errors and cancellation signals.

The build publishes canonical URLs, unique titles and descriptions, Open Graph/Twitter metadata, WebSite/WebPage structured data, `sitemap.xml`, `robots.txt`, and a custom noindex 404 page. Search results and player lookup are excluded from the sitemap. Individual player results are marked noindex; live feeds and player data are never captured during the build. The existing attribution and artwork source links remain intact. The public Google verification tag in `docs/index.html` must remain for Search Console ownership verification.

The pre-SEO rollback branch is `seo-rollback-2026-11-20`, commit `82f9956c3f1a016d1432b08e93e7e1e8cd5d3f62`. To fully revert, restore the pre-SEO source through a new commit and change Settings → Pages → Source back to **Deploy from a branch**, **main**, **/docs**. Preserve the custom domain and HTTPS settings. Reverting does not immediately remove search-engine caches.

The public community API is `https://microscape-wiki-api.pages.dev/`, configured once in `docs/api-config.js`. Its Cloudflare Pages Function forwards only the five read-only wiki endpoints through the `LIVE_DROPS` service binding to the `microscape-live-drops` Worker. Build output is `api-gateway`; no build command or copied Twitch credentials are needed. Redeploy after configuring the production binding. The Worker fetches the game’s stream list on demand and caches each response for one minute. The wiki checks on page load, every five minutes while visible, and when readers click **Refresh**. Deploy backend changes separately from the `workers` directory; publishing the wiki does not update a manually deployed Worker.

The same Worker serves `/mzdunk.json` for Twitch status. Set `TWITCH_CLIENT_ID` as a Worker variable and `TWITCH_CLIENT_SECRET` as a Worker secret from the wiki’s dedicated Twitch app. The wiki checks Twitch every minute while visible and immediately on tab visibility, focus, page restoration, or reconnection. Concurrent Twitch checks share one request. The wiki uses Microscape’s stream list as a fallback while Twitch status is unavailable. When the last confirmed live status is too old, the sidebar keeps the channel link visible with a Checking badge until another check confirms whether she is live or offline.

If the live feed is unavailable, the tracker tries `/drops-backup.json` through the same neutral API. Configure the backend Worker's `DROPS_BACKUP_URL` variable to the raw `drops.json` URL from this repository's `live-data` branch. Keep that deployment setting server-side. The **Refresh live Microscape drops** GitHub Actions workflow can publish that fallback automatically or run manually from Actions. If both sources are unavailable or more than 40 minutes old, the tracker directs readers to Streams in Microscape.

Microscape can return a server error for an exact username without a public character profile. Player Lookup explains this and offers full-name suggestions; it does not cache failed profiles or treat every upstream failure as a missing player. Location, activity and world restrictions described above still apply.

Use the neutral repository-local commit identity `Microscape Wiki Community <wiki-community@users.noreply.github.com>` for community updates. Public browser requests and page links should use the community API and community channels rather than personal hosting identifiers.

## Interactive Locations map

The `/locations/` directory starts with the original game world map. Scroll-wheel
zoom stays anchored to the cursor, dragging pans, and pins open existing location
pages. Zoom buttons, arrow keys, +/- and Home provide keyboard controls. The search
indexes activity outputs, shop stock, NPCs, skills and enemy drops rather than
ingredients merely consumed at a location. Pet/Pets selects the Mork/Otis map hub.
Exact enemy names select their combat locations. Food searches omit cooking and
food-preparation recipes; search Cooking for fire/cooking-table locations instead.
Gathering, raw-item drops, shop stock and cooking-pet sources remain searchable.
One matching location is centered, while multiple matches preserve the map view.
Interior chambers highlight their entrance and keep their own result-page links.
The full location directory remains below the map.

Rebuild the search and pin data with
`node scripts/build-world-map-data.mjs GAME_DATA_JSON CLIENT_JS` and run
`node scripts/check-world-map.mjs`. The source hash and original artwork URL are
recorded in `docs/world-map-data.js`; asset credits are in `docs/assets/maps`.

## Sprite hover previews

Full sprites on Foes, Pets and Player Lookup preview the game's idle and combat
motions on hover or keyboard focus. `docs/sprite-animation.js` uses the original
pet frame sequences and the public client's animation timings and transforms;
Player Lookup applies those transforms to the player's existing equipment layers.
Previews stop when focus or the pointer leaves, on navigation and in hidden tabs,

## Bazaar

The Compendium's `#/bazaar` page combines the trading guide with a searchable,
read-only public market. `docs/bazaar.js` filters and sorts item summaries, then
loads both order books and recent trades for a selected item. Price sparklines,
deviation from the recorded 30-day average, recorded lows, and an interactive
timestamp-scaled chart supplement current orders. Watchlists store only item IDs
in the reader's browser; no account, notification subscription or trade is created.
Item names and
icons use the wiki catalog; item detail links preserve established wiki routes.
The existing `#/entry/bazaar` guide remains available and links to the market.
Edit its explanation in `docs/guides.js`. Verified client constants and source
hashes are preserved in `docs/assets/game-data/bazaar-2026-11-20.json`.

The neutral gateway's `/bazaar.json` endpoint reads the official public
`bazaar.getAllItemSummaries` procedure. Add `?item=ITEM_ID` to read
`bazaar.getItemMarketSummary` and each side of `bazaar.getItemOrders`.
Only named market fields are returned. No account cookies, private order
history, Twitch tokens or trade mutations are used. The gateway caches each
public response for 30 seconds; the page refreshes every 30 seconds while
visible and cancels its polling and pending requests when readers leave.
Errors retain a clearly labeled last successful snapshot instead of reporting
an empty market. Run `node scripts/check-bazaar.mjs` to verify this API.
The existing local preview command also serves the public Bazaar endpoint.

Public order feeds expose no buyer/seller identity. The game's `(you)` label
matches IDs against the authenticated player's private My Orders list; it is
not a public username lookup. The source trace and anonymous endpoint results
are recorded in `audits/2026-11-22-own-market-history.md`.

Market column headings are buttons: click to sort and click again to reverse.
Sorting applies to all matching items before pagination, with missing values last.
Recent prices sorts by net percentage change across recorded samples and loads
history for all matching items in batches of 30. Prices, averages, lows, and each
quantity can also be sorted; the dropdown stays synchronized. Sorting survives
market refreshes and filters, and keyboard focus remains on the selected heading.

`/bazaar-history.json` uses our private `microscape-market-history` Worker through
the Pages `MARKET_HISTORY` service binding. The collector in
`workers/market-history.mjs` polls only the official public
`bazaar.getAllItemSummaries` endpoint on `*/15 * * * *` (UTC). The dedicated D1
`MARKET_DB` stores per-item asking/bidding prices and total quantities, with no
player, account or cookie data. The SQLite schema initializes automatically.
No other wiki supplies or backfills our history. A first read can bootstrap the
empty database once; after that only cron advances collection. `lastScheduledAt`
and `lastPoll` report real scheduled activity and successful collection separately.
Duplicate events in one 15-minute bucket do not double-count samples or averages.

Raw samples retain 14 days. Daily rollups retain 400 days; lifetime lows and the
collection start date persist beyond that. Averages are weighted by observed
sample counts, not traded volume; 7/30-day summaries use UTC calendar days. The
24-hour low uses the precise trailing time window. Failed upstream reads leave
stored history intact, and a delay beyond three sampling intervals is flagged.
Cleanup runs daily. The schema uses primary-key-only WITHOUT ROWID tables to
limit indexed writes. Summaries are materialized once per collection, so visitors
read a small stored result instead of rescanning 24-hour/30-day windows. Lows and
averages are as of the last successful sample. Late events cannot regress metadata.
Check D1 usage as market coverage/traffic grows; no paid plan
is enabled by this setup. Future CLI deploys must use
`wrangler deploy --config workers/market-history.wrangler.toml` so the cron, private
endpoint setting and D1 binding are preserved.

The history API provides summaries, `?item=ITEM_ID&range=7d` charts, and
`?ids=A,B` sparklines for at most 30 IDs. 24h/7d charts show sampled asking prices;
1m/3m/6m/12m/all show daily averages. It caches for five minutes under a new cache
namespace, never reusing old third-party history. Missing data is not zero and
historical prices never become current orders. Run
`node scripts/check-own-market-history.mjs` for actual SQLite collection,
idempotency, failure, exact window and retention tests, and
`node scripts/check-market-trends.mjs` for service binding/cache/UI math checks.
Cloudflare Pages automatically deploys `api-gateway` from main; the separate
collector Worker is deployed with its own configuration. LIVE_DROPS is unchanged.

The shared visual walkthrough in `docs/bazaar-walkthrough.js` appears on both the
market page and the existing guide. Its seven original in-game screenshots are
in `docs/assets/bazaar`, with capture notes there. Keep captions and example
arithmetic consistent with those static images; market prices and times change.

Run `./scripts/register-drops-backup.ps1` in PowerShell 7 to register the optional **Microscape Wiki Live Drops Backup** task. Pass `-Replace` to update the existing task. It runs every 15 minutes while its user is signed in and the PC is awake, and publishes to `live-data` using the existing GitHub sign-in when the snapshot is at least 10 minutes old. Check `last-run.log` in the task’s state directory for the latest result. To stop the backup, disable the named task in Task Scheduler.

## Leaderboards and player ranks

`/leaderboards/` appears under Explore. `docs/leaderboards.js` provides a
searchable selector for the game's ranked Twitch community directory, global or
community scope, total-level ranking, and all 16 skills in game order. Each
player links to Player Lookup. The profile adds an independent Overall rank
request; ranking errors do not hide the profile, equipment or skills. Its rank
link opens the leaderboard with that player selected and highlighted.
The selected row is centered and focused once after it loads. Every cell in the
row is highlighted; routine ranking refreshes do not repeat the scroll.

The neutral API gateway reads the official public `communities-with-highscores`, `leaderboard`
and `user-ranks` procedures through `api-gateway/leaderboards.js`. Public routes
are `/communities.json`, `/leaderboard.json?community=all&skill=all`, and
`/player-ranks.json?id=TWITCH_ID`. An optional `player=TWITCH_ID` on the board
asks the game to include that player's row. The game requires a user context;
the anonymous board uses the verified neutral value `0`, never an owner's ID.
The game normally returns the leading 200 rows, adding the selected player
when available; rank gaps and missing player ranks are preserved. Overall is
the game's total-skill-level ranking, not a locally calculated XP ordering.

Community lists cache for five minutes in a namespace separate from the former
unfiltered directory; boards and ranks cache for one minute. Communities without
ranking entries are excluded using the game's own high-score directory. Old
links to excluded communities fall back to the global board. Manual Refresh
also reloads the ranked-community choices.
Filters and player context use separate cache keys. Queries are allowlisted,
public fields are normalized, and failures are not cached as empty data. No
cookies, credentials, sockets or character actions are used. The page polls
every minute while visible and cancels pending work when navigating away.
`node scripts/check-leaderboards.mjs` verifies these rules. The local preview
serves these same endpoints using only public game reads.

## Site analytics

`docs/analytics.js` connects the separate Microscape Wiki GA4 property using the
public Measurement ID `G-90EN0H2GM4`. It loads Google's tag once on the production
domains and records one page view per canonical route after rendering. Automatic
history page views are disabled in the web stream to prevent double counting;
site-search and form-interaction measurement are also disabled. Scroll, outbound
click, video and file-download enhanced measurements remain enabled.

Page-view locations exclude query strings/fragments; initial referrers retain
only their origin and subsequent referrers use the preceding canonical route.
No player/profile payloads or user IDs are passed to Analytics. Google signals
and advertising personalization are off. Prerendering, localhost previews, DNT
and GPC produce no tag or events. `node scripts/check-analytics.mjs` verifies
route counting, navigation, redaction and these guards. The About page discloses
analytics. Removing the import/call in `docs/app.js` disables this integration.

## Activity Planner and BETA-Activity Queue

The Activity Planner guide (`/guides/activity-planner/`) contains the original
browser-only material and XP/time planner for up to 20 steps.
It selects activities by skill and item, supports action/kill, level, inventory
and indefinite targets, and carries guaranteed materials and XP forward in order.
Base skilling estimates exclude Double Ups, active abilities, potions, travel and
resource waits. Combat reuses the existing comparison model and its XP-rate
limitations. Unmodeled or indefinite steps produce partial totals rather than a
false full-plan estimate.

Good Magic includes Low/High Alchemy with a selected conversion item. The planner
consumes that item plus runes and calculates the client's gross coin proceeds
(base value plus the larger of 10% floored/1 coin for Low, or 50% floored/2 coins
for High). Saves, share links and item-count goals retain the chosen item. It also
includes Enchant Amulet 5 with a manual restart note, and Dark Ritual with its
Death's Bargain requirement, Evil Magic XP and no guaranteed random shard output.
The shared BETA-Activity Queue also records alchemy's chosen item. This remains
wiki-only planning; no actions are sent to the game.

Working drafts and up to 30 named plans stay in local storage. Shared plans use
validated, versioned data in a URL fragment, including starting XP, base gear and
inventory counts; the lookup username is not copied. Players enter all steps
manually in-game. The planner never connects to the game's signed-in socket or
sends character-control commands. Its existing storage keys remain unchanged.

The separate Activity Queue guide (`/guides/activity-queue/`) models the Guild
membership queue: activity plus stopping condition, or a custom equipment
loadout change, in sequence. Its initial example is 100 Raw Shrimp → a configured
bronze Melee loadout → 20 Cow kills. Equipment is selected per slot with icons,
requirements and item links. Empty slots mean unequip. Weapon/shield conflicts
use the existing Gear Comparison rules. Configurations are included in saves
and validated `#queue=` share links. Earlier saved-slot references remain visible
with a prompt to configure them, since their gear was never known. The player
recreates and saves each setup in-game before selecting it in the game's queue.
Old `#plan=` links on this guide offer a link to Activity Planner instead.

The beta queue reuses the public username lookup/suggestions to seed new
loadouts with current equipped items. The public character response has no
inventory field (rechecked November 24). Gear choices are restricted to equipped
items plus extra items the reader manually confirms owning. Availability stays
in memory for the visit; no username, inventory claim or lookup snapshot enters
saved/shared queues. Refreshing or changing players requires new confirmation;
refreshing the same player retains manual confirmations for that visit. Saved
queue gear never establishes ownership. Unavailable saved selections remain
visible but disabled and flagged; committing a loadout or copying the manual
setup is blocked until they are replaced or confirmed. Quantities/charges and
level requirements are not checked. Requests/timers are canceled on name changes
and navigation; late responses cannot overwrite a newer lookup.

`node scripts/check-queue-planner.mjs` checks material chains, sequential targets,
combat, invalid imports, sharing and the step limit. `node scripts/check-membership-queue.mjs`
checks mixed activity/loadout steps, stopping rules, saved slots and share validation.
Refresh the committed data
with `node scripts/build-queue-catalog.mjs PATH_TO_EXTRACTED_GAME_DATA_JSON` after
updating the main activity catalog. The Activity Queue is published as a beta,
linked last in Resources as **BETA-Activity Queue**, and remains under refinement.
